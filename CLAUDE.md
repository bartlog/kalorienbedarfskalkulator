# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A calorie needs calculator (Kalorienbedarfsrechner), bilingual UI (German/English, switchable in the header, German is the source of truth). Deliberately client-side only: no server, no build step, no dependencies. All input and calculation happens in the browser; nothing is transmitted anywhere. Intended for static hosting on GitHub Pages directly from the repository root.

## Running

Open [index.html](index.html) directly in a browser, or serve the directory with any static file server. There is no build, bundle, or install step — do not introduce one (e.g. npm/Vite/webpack) unless the user explicitly asks for it, since "no server, runs locally in the browser" is a stated requirement, not an accidental omission.

## Architecture

Namespace pattern (`window.KBR = window.KBR || {}`) instead of ES modules, so the page keeps working when opened via `file://` (double-click, no server). Script load order in [index.html](index.html) matters because of this.

- [index.html](index.html) — four tabs ("Rechner" / "Methodik & Quellen" / "Über" / "Tipps", the last right-aligned via `margin-left: auto` on its tab button to visually separate it from the first three). Rechner tab: progressive-disclosure form (Kategorie A always visible, Kategorie B in a `<details>` block) plus a hidden result section revealed after submit. Methodik tab: static formula-sources list + info panel, both rendered from JS data at load time. Über tab: static project/author info. Tipps tab: filterable accordion sections rendered from `js/tipps-daten.js` (see below).
- [css/style.css](css/style.css) — all styling, CSS custom properties for the color palette, `@media print` with `@page { size: A4; }` for the PDF export. Contains a load-bearing `[hidden] { display: none !important; }` rule near the top — without it, any class that sets `display` (e.g. `.field { display: flex }`) silently wins over the browser's default `[hidden]{display:none}` because both have equal specificity and the author stylesheet loads after the UA one. Any new `[hidden]`-toggled element depends on that rule; don't remove it. Also has a `.druck-eingaben` block (see `ui.js`) forced onto its own page via `break-before: page` for a second PDF page listing the raw entered values (third+ page if many MET rows overflow it) — `:not([hidden])` guards it so printing before ever calculating doesn't show an empty page.
  **Verifying print/PDF layout:** `page.evaluate()`-measured `scrollHeight` under `page.emulateMedia({media:'print'})` does *not* reliably predict actual `page.pdf()` pagination (confirmed twice — height math said content fit when the real PDF still overflowed by up to a full line). Always regenerate the actual PDF via Playwright's `page.pdf()` and inspect page count/text-per-page with `pdfjs-dist` (`legacy/build/pdf.mjs`, install alongside `playwright` in one `npm install` command — installing either alone prunes the other since neither is saved to the scratchpad's `package.json`) rather than trusting height calculations alone.
  **`.druck-footer` (2026-08-19):** repeating per-page print footer (date + optional free text from `#druckFussnote`), implemented via `position: fixed` inside `@media print` — Chromium repeats `position: fixed` elements on every printed page reliably in practice, even though this isn't governed by a CSS Paged Media spec mechanism the way `@page` margin boxes are. Deliberately has **no** page-number output: Chromium doesn't support `@page` margin-box counters (`counter(page)`/`counter(pages)`) in either the browser's own print dialog or Playwright's `page.pdf()`, and there's no dependency-free way around that (see `ui.js` above). `.print-footer-feld` (the on-screen input+label for the footer text) is hidden in print the same way as `.secondary-btn` etc. The new "Gewichtsstillstand" info panel (`.stillstand-panel`, a `<details>` reusing the `.result-details`/`.hint-box` pattern) needed no new CSS — it inherits the same collapsed-by-default print behavior as the existing "Details zur Berechnung" panel (a `<details>` without `open` stays collapsed in print unless the user expands it first).
- `js/formeln.js` — REE formula registry (`REGISTRY`), five pure formula functions (Mifflin-St-Jeor, Cunningham 1991 / Katch-McArdle, Ten Haaf & Weijs 2014, Müller BMI-graduiert — obesity tier only, see `auswahl.js` note below, Lührmann). Formula *names* are proper nouns and stay language-neutral; `quelle` (citation + explanatory prose) is bilingual (`{de, en}`) since it's more than a bare citation. Also `ffmAusKfa` (derive fat-free mass from weight + body-fat %). `tenHaaf({ffmKg})` takes **only** `ffmKg`, per the actual Ten Haaf & Weijs (2014) FFM-based equation — it has never taken a height parameter. A 2026-08-19 request described a "weight-based Ten-Haaf formula expecting height in meters" needing a cm→m safety conversion; that formula/bug doesn't exist here (confirmed by reading the code), so nothing was changed. Don't add a height parameter to `tenHaaf` without first verifying against the actual paper — the request's premise may have been based on a different Ten-Haaf variant or a hallucinated analysis.
- `js/auswahl.js` — `selectREE(p)`, the precedence decision tree that picks a formula based on measured FFM / pregnancy / obesity (BMI≥30) / age. Pure, no DOM, and language-neutral: returns `begruendungId`/`begruendungParams` and `hinweise` (an array of ids) instead of formatted text — `ui.js` resolves these through `i18n.js` at render time. Underweight (BMI<18.5) has **no dedicated branch** — it falls through to Lührmann (if age≥65) or Mifflin (default). Müller used to also cover underweight, but that tier was removed (see `formeln.js`) after a 2026-08-19 test case showed 35–70% lower REE than Mifflin across the whole underweight range, vs. only ~2% divergence at the obesity-branch boundary — evidence the underweight coefficients were mistranscribed, not a real formula property. Don't re-add an underweight-specific formula branch without re-verifying coefficients against the actual Müller 2004 paper first (web-fetch of it was previously unreliable, see the coefficient-sourcing note below).
  **Soft boundaries:** at the two hard thresholds (BMI 30, age 65) the branch decision stays a hard cutoff for the *primary* formula that feeds the rest of the pipeline, but within ±1 BMI point (29.0–31.0) or ±5 years (60–69) the return object also carries `vergleich: {formelId, formelName, reeBasis}` — the *other* formula's raw REE, for side-by-side display only (`softBoundary: 'bmi'|'alter'|null` says which zone). `ui.js`'s `renderSoftBoundaryHinweis` shows both values plus an explanatory hint; nothing downstream (TEE, Ziel, protein, uncertainty band) uses `vergleich` — it's purely informational. If both zones apply at once (e.g. BMI 29.5 at age 62), only the BMI comparison is shown, matching the tree's own BMI-before-age precedence.
- `js/modifikatoren.js` — modifier catalog classified by `wirkung: 'ree'|'pal'|'tee'|'hinweis'`, plus the axis-guard (`kombiniereReeFaktoren`) that prevents same-axis REE modifiers from multiplying together. `HINWEIS_IDS` lists the factors deliberately *not* computed (TEF, sleep duration, subjective stress, caffeine, luteal phase) — their label/reason text lives in `i18n.js` under `hinweis_<id>_label`/`hinweis_<id>_grund`, shown to the user, never silently dropped. `MET_AKTIVITAETEN` is likewise language-neutral (`id` + `kategorieId` + `met` only); display labels live in `i18n.js` under `met_aktivitaet_<id>`/`met_kategorie_<kategorieId>`.
  **PAL layer (NEAT/Sport/Fidgeting, 2026-08-19):** `NEAT_STUFEN`/`neatPalBereich` (steps-based daily-activity PAL *range*, `palMin`/`palMax` per tier — not a single value, since the tier itself already carries real-world spread) and `SPORT_HAEUFIGKEIT_STUFEN`/`sportHaeufigkeitZuschlag` (frequency-based, additive PAL zuschlag, flat `min===max`) plus `fidgetingPalZuschlag` (small additive band) replace the old single `basisPAL` dropdown. These are combined by simple addition in `berechnung.js`, **not** via an `achse`-tagged guard like `kombiniereReeFaktoren` — that pattern exists for REE factors that can legitimately compete over the same physiological axis; NEAT/Sport/Fidgeting don't collide by construction (Sport-dropdown and MET are mutually exclusive via the UI radio, exactly as before — see `ui.js` below — and Fidgeting is deliberately orthogonal to both). Don't assume the same "strongest wins per axis" semantics apply here; they don't.
  **`laufIntensitaetsZuschlag` (2026-08-19):** an optional, always-available (independent of the Sport radio/MET) PAL-equivalent add-on for runners, following `sportMet`'s shape exactly (needs `reeAdj`, returns a flat `{min, max}` PAL-equivalent). Computes only the *intensity delta* of running over walking (`kmWoche * weightKg * 0.5 / 7` kcal/day, ÷ `reeAdj`) — **not** the full running energy cost — because the NEAT step count already covers the base distance at an implicit walking-pace assumption; adding the full running cost on top would double-count the distance itself. The `0.5 kcal/kg/km` coefficient is a commonly-used approximation for that net delta (running gross ≈1.0, brisk walking gross ≈0.5 kcal/kg/km), not a single-study citation — treat it the same way as the `sportMet` MET-1 formula (a standard approximation, fine to use as-is, but don't present it to users as more precise than it is). This is the precise alternative to the text-only double-counting guidance for Sport-Häufigkeit/MET's `laufen`/`gehen_wandern` categories (see `ui.js`/`index.html` disclaimers) — the disclaimers now point runners here instead of just warning them away.
- `js/berechnung.js` — the pipeline (REE_basis → REE_adj → PAL_adj → TEE → goal adjustment), the Root-Sum-Square uncertainty band, plausibility clamps, and the two extra reference values (fat-loss calories, protein needs for maintenance/growth — the latter switches its reference weight from total body weight to FFM when BMI ≥30 and FFM is known, per PLAN.md). `sammleAktiveModifikatoren` returns structured `{id, ...raw numbers}` entries (not formatted strings) — `ui.js`'s `formatiereModifikator` turns them into text via `i18n.js`, so number formatting (decimal/thousands separators) stays sprache-aware in one place.
  **PAL_adj (2026-08-19):** `berechnePalMitBand` sums three independent components instead of reading one `basisPAL` number — NEAT (`eingabe.neatSchritteId`, a range), Sport (`eingabe.sport.haeufigkeitId`, flat, **replaced** rather than added-to when `eingabe.sport.modus === "met"`), and Fidgeting (`eingabe.fidgetingAktiv`, flat band, always additive regardless of sport mode). The `[1.2, 2.4]` PAL clamp was raised to `[1.2, 2.6]` — the old ceiling was calibrated to the single old dropdown's max (1.9) plus a small MET zuschlag; the new three-source sum can legitimately reach 2.5 at the dropdown extremes (NEAT max 2.0 + Sport max 0.4 + Fidgeting max 0.1) and higher still with an extreme MET entry, so 2.4 would clip valid results. `berechne()`'s returned `pal.hochWarnung` (`palAdjHaupt >= 2.4`) drives a non-blocking UI hint about sustained metabolic load — it does not affect the calculation itself. This replaced the old `eingabe.basisPAL` (single number, 5-option dropdown `1.2–1.9`) — an accepted breaking change to the opt-in `localStorage` form data (no migration code; small/personal-use audience, and the raw dropdown value never carried meaning beyond "what was last selected").
- `js/speicher.js` — opt-in `localStorage` persistence of raw form values (not results). Language preference is a separate, always-on `localStorage` key (`kbr:sprache`, in `i18n.js`) — it's a UI preference, not personal/health data, so it isn't gated by the same opt-in checkbox.
- `js/i18n.js` — the DE/EN dictionary (`STRINGS`, flat keys → `{de, en}`) plus `t(key, params)` (simple `{{name}}` substitution), `zahl(value, decimals)`/`zahlNatuerlich(value)` (locale-aware number formatting: `de-DE` vs `en-US` separators), and `getSprache()`/`setSprache()`. Pure data/functions, no DOM — mirrors the "no DOM outside ui.js" rule from the calculation files.
- `js/tipps-daten.js` — static content data (`window.KBR.tipps.ABSCHNITTE`, array of `{id, titel:{de,en}, spalte1/2/3:{de,en}, zeilen:[{stufe, de:[...], en:[...]}]}`) for the Tipps tab: curated fat-loss/recomposition guidance (nutrition, food/drink, restaurant behavior, training, supplements). `stufe` is a language-neutral code (`top`/`gut`/`ok`/`selten`/`vermeiden`, or a phase code for the restaurant table) used for filtering and the CSS row-color class; `STUFE_LABELS` maps each code to its `{de, en}` display text. This is a manually-updated snapshot of a private Google Sheet the user maintains, in German only — the sheet's URL is deliberately *not* in this repo (see memory `reference_tipps_spreadsheet` for the fileId and the regeneration workflow). **The English text is a manual translation, not part of the sheet** — when the user says the sheet changed, re-fetch it, update/add the German row(s), and translate the same row(s) into English; don't skip the translation step.
- `js/ui.js` — the only file touching the DOM: tab switching, conditional field visibility, reading the form into the pipeline's input shape, rendering results (including the inline-SVG bar/band graphics, the BMI line, and `renderSoftBoundaryHinweis`), rendering the Tipps accordion/filter UI (`renderTipps`), wiring save/delete/print buttons, and `wendeSpracheAn()` — the single function that applies the current language: walks every `[data-i18n]` element (sets `innerHTML` from `i18n.t()`, so translated strings may contain trusted static markup like `<strong>`/`<abbr>`/`<a>`), re-renders the language-dependent dynamic sections (Methodik formula list, "not included" hints, Tipps tables, MET dropdown labels), and — if a result is already showing — re-renders it from the cached `letztesErgebnis`/`letzteEingabe` so numbers reformat and generated text (formula rationale, active-modifier list, warnings) re-translates without recalculating.
  **`validiereEingabe(eingabe)`** runs on submit, before `berechne()`: blocks the calculation and shows a message under the relevant field (`.field-error`, `#error-kfa`/`#error-ffm-direkt`/`#error-fieber`) for body-fat % outside 3–60, direct FFM entry ≥ body weight, or a fever temperature outside 35.0–42.0°C (with a distinct message above 45°C — likely a Fahrenheit entry). Reads the DOM directly rather than the already-parsed `eingabe` object where the two disagree (e.g. `eingabe.fieber` is `null` whenever temperature ≤37°C, "no active fever", which is a different question from "is the raw field value plausible"). This validation is intentionally a `ui.js`-only gate, not part of `berechnung.js` — the calculation pipeline stays a pure function with no error/validation state.
  **`anwendenMetUeberschreibung` (2026-08-19)** now targets `#sportHaeufigkeit` (disables it, forces `"keinSport"`) instead of the old `#activity` — it exists because Sport-dropdown and MET describe the same axis (training intensity) and would double-count if both applied. `#neatSchritte` (daily-activity/NEAT dropdown) is never touched by this override; NEAT and Sport are independent PAL inputs (see `modifikatoren.js`/`berechnung.js` above). The print button handler also populates `#druck-footer-datum`/`#druck-footer-text` from `#druckFussnote` right before `window.print()` — that field is optional free text (max 20 chars) shown centered in a `position: fixed` footer that repeats on every printed page (see `css/style.css` below); it does **not** attempt page-number ("Seite X von Y") output, since Chromium's print pipeline doesn't support CSS `@page` margin-box counters and adding a PDF library to compute/render page numbers would violate the no-dependencies constraint.
- [tests.html](tests.html) — in-browser test runner (no npm), exercises `formeln.js`/`auswahl.js`/`modifikatoren.js`/`berechnung.js` directly. Open by double-click; results render as a pass/fail list in the page. Doesn't touch `i18n.js`/`ui.js`, so it's unaffected by translation changes.

When changing the calculation, keep it in `formeln.js`/`auswahl.js`/`modifikatoren.js`/`berechnung.js` as plain functions of primitive values (no DOM access, no language-formatted strings — return ids/params instead) — that's what makes `tests.html` possible and keeps translation centralized. DOM work and all display/number formatting belongs only in `ui.js`.

**Adding any new user-facing string** (new field, new hint, new dynamic message) means adding both a `de` and an `en` entry to `i18n.js` and wiring it via `data-i18n` (static HTML) or `i18n.t(key, params)` (dynamic JS) — there is no "just hardcode the German for now," since the language switch has no fallback for missing keys beyond echoing the raw key string.

The formula coefficients for Ten-Haaf, Müller, and Lührmann came from the user's own Gemini-assisted research (not independently re-derived here) — web search/fetch in this environment could not reliably extract exact published coefficients from the source papers (PDF table extraction produced physiologically implausible results, e.g. negative REE). If those coefficients ever need revisiting, don't re-trust an automated web fetch of the paper without sanity-checking the output against plausible REE values first.

## Conventions

- UI copy is bilingual (German source of truth + English), see `js/i18n.js`. Keep new user-facing strings consistent with existing tone in both languages (labels, buttons, disclaimer). Never leak internal identifiers (function/variable names) into user-facing copy. Use **"Grundumsatz"** consistently for REE in German — not "Ruheumsatz" (same concept, but mixing both terms in the same UI confused a user in testing).
- The English strings are machine-translated by the assistant, not professionally reviewed — the app shows a small notice to this effect whenever English is active (`#translation-notice` in `index.html`). Don't remove that notice without the user explicitly asking to.
- No external requests, analytics, or third-party scripts — the "runs entirely local in the browser" constraint is a hard requirement from the project's purpose, not a style preference. The font stack (`Roboto, -apple-system, "Segoe UI", ...`) relies on locally installed fonts only, no web-font loading.
